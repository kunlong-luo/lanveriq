# V0.1 批量开发、集中验收与上线计划 / Batched delivery plan

**批准日期：2026-11-08。状态：执行中的 v0.1 研发策略，不是生产发布批准。**
**决策：**优先打通真实业务闭环，停止无目的的前端微调、逐小提交全量重测和以 NXT 序号代替业务里程碑。已有 D0 架构批准仅允许源码研发与隔离合成验收；**不授权采集真实员工/终端数据、启用生产管理员、部署 Agent 或屏幕录制**。

## 目标和明确排除项

**首版 v0.1 可用目标：**由管理员批准的测试设备使用审查过的证书注册、激活、撤销，经受限 mTLS 链路上传心跳、硬件/OS/存储清单和受限事件；Spring Boot 以 PostgreSQL 18 持久化，客户端以 SQLx/SQLite 保留重试数据；Next.js 在服务端授权后显示真实、具有接收时间和未知/过期状态的终端资产与监控；断网/重启/凭证撤销/跨组访问均按安全规则处理；受限 REST + WSS 提示及 REST 重同步。首轮只在**获授权的隔离测试环境**验证。

**不阻塞 v0.1 的后续范围：**v0.2 审计/应用活动、复杂报表与策略；v0.3 有显式同意的屏幕录制/审批/回放；高级告警、导出与长期视频保存。这些页面可继续作为明确标注的规划页，不能标成已交付业务能力。

## 当前基线（以源码和 2026-11-08 CI 为准）

- 前端：Next.js 16.4.5、B+C 设计、11 个预览路由和隔离/CI-only 已授权设备交互模型已实现；公开 Pages 静态站点**断开 API、无登录、无真实设备数据**。alerts/policies/reports/design-system 等不是已上线的业务端点。

- Agent：Rust/SQLx SQLite、离线 outbox、清单模型、传输/ACK、服务框架与策略决策逻辑有独立实现；**自动采集/上传/证书身份/服务生命周期尚未真正连接成端到端可运行链路**。

## 按业务闭环而不是 NXT 编号组织开发

**2026-11-08 原始协议审查结论（历史）：**当前设备通信明确使用 Rust `reqwest` + `rustls` + Serde JSON，经独立 client CA 的 Caddy mTLS 和固定上游 client-auth=need 到 Spring/JPA/PG18，配合 SQLx SQLite outbox 和精确业务 ACK。保留 REST/mTLS 直到 v0.1 核心链路验收完成；gRPC/Protobuf(`tonic`/`prost`+Spring gRPC+Buf) 是未来性能候选，MQTT 5.0 非首版必需。**批次 A 新增 P0：**评审 Rust 客户端 `TLS_1_2` 最低配置与完整 TLS1.3 目标的差距，Agent→Caddy+上游两段真实握手拒绝负例；同时制定 Rust/Java JSON golden fixtures、首个心跳 ACK 兼容性和设备证书 custody/轮换证明。详见 [设备协议栈](../architecture/device-communication-stack.md) 和 [文档审查报告](../governance/documentation-audit-2026-11-08.md)。不在文档阶段直接改生产 TLS 配置或启动 Agent。

## 并行接入轨道 R — RustDesk 与 LAN/WAN 双网络（2026-11-08 新批准方向）

用户确认 Lanveriq 必须面向获授权的**内网和外网**使用，底层远程桌面、NAT 穿透/ICE 和 Relay **优先复用 RustDesk**。此轨道按 [ADR-0011](../architecture/adrs/0011-rustdesk-dual-network-access.md) 和 [双网络验收](../operations/dual-network-acceptance.md) 推进，与 A–E 的身份、心跳、库存和用户授权保持独立，不能因远程桌面可连就声称设备业务闭环已通过。

R1：只读网络契约、许可和 API 核验、RustDesk OSS/Pro 版本锁定及威胁模型。R2：隔离环境内的 RustDesk hbbs/hbbr + Windows/Linux 客户端，内网 P2P，真正外网/VPN P2P/Relay，记录连接状态、断网/重启/撤权和带宽/延迟。R3：Lanveriq 设备权限到远程会话的最小安全适配器（必须先证明产品 API/嵌入/许可可用），不自行实现私有协议。R4：以一个正式自持域名和 LAN split DNS / WAN VPN 进行双视角 Console HTTPS、Origin/CSRF/RBAC/缓存/直接上游拒绝和密钥/备份验收；单独批准之后才允许公网 Console 443。R1/L1 与 R2/L2 在沙箱中可并行，R3/R4 真实系统启用必须等待 A–E 和隐私、授权门槛；不得修改已有共享 `spark-db`、真实设备采集和默认关闭的业务路由。

## 新的三级测试模型（Approved）

1. **L1 快速反馈：每次源码改动**。按路径触发 Java JUnit/Gradle 编译、Rust `cargo test --locked`/Clippy、Next.js Vitest/TypeScript、源代码安全/配置检查。与改动无关的模块不跑。**权限、凭据、证书、迁移、ACK、输入验证的负向单元测试仍必须伴随源码改动。** 可移植 Agent 代码的日常 L1 在 Linux 执行 Rustfmt/test/Clippy；Windows SCM、启动/运行时配置与依赖变更由单独的 `agent-windows-targeted.yml` 立即验证，所有 `acceptance/v0.1-*` 里程碑标签都必须跑一次原生 Windows 检查。之前普通 transport 变更触发双平台耗时约 5 分钟，新分离策略避免这类重复等待。 减少不必要的重复 Springdoc/Orval/bootJar/Testcontainers 编译，仅当契约或服务边界变动时运行。
2. **L2 子系统/批次集成：业务批次准备验收时一次执行**。PostgreSQL 18 Testcontainers、Agent SQLite/HTTP 合成数据、Caddy/Tomcat mTLS 与边界/权限负例。为单一失败用例允许定向复测；修复后再跑受影响的批次完整集。所有测试仅在一次性 CI/沙箱、synthetic-only 环境运行。
3. **L3 里程碑/发布候选：完整安全/跨平台验收**。真实 Chromium 11 路由、15 张视觉截图、A/B 管理员/RSC/HTML/CSRF/撤销、全 PostgreSQL suite、Windows/Linux 安装和服务生命周期、数据恢复/故障演练/渗透与隐私批准。在**明确的里程碑标签**或 `workflow_dispatch` 下运行并保留 SHA/日志；不在普通代码/样式提交上重复触发。

**CI 触发约定：**普通 `main` push 仅触发路径过滤的快速 CI；昂贵的 `console-https-synthetic`、`nextjs-browser-preview-synthetic` 改成 `workflow_dispatch` / 形如 `acceptance/v0.1-*` 的里程碑 Git tag。公共 Pages 发布只在显式演示评审时触发，不因内部服务代码变化而部署；除非产品另行批准，仍只允许生成断开的静态页面。保留手动 PostgreSQL/PKI 测试的分离安全策略。**不得通过跳过单元/负向安全检查来追求 CI 绿色。** 必须给真实上线附条件，而非将合成绿灯视作批准。

## 调整后的实施次序

1. 先将本策略写入 roadmap、test strategy、release、backlog、AGENTS.md。使这些文档不再宣称 v0.1 “尚未开始”或日常 CI “必须完全 unit-only”。
2. 再将 GH Actions 重型工作流改为 **tag/dispatch**，修正触发条件使 tag 下执行全部合成门禁；保留 `main` 快速路径检查并为服务端生成契约提供合适的按路径细分。
3. 从 **批次 A** 开始：先审查/实现可重复的合成设备身份→心跳→PG18 一跳及其前置的安全契约；之后连续补足证书生命周期/Agent 运行桥接，而非再做新大屏/UI装饰。
4. 每批结束集中集成，发现失败时修复，不伪称完成。不主动采集、安排或上传真实设备/员工数据，不启用默认 OFF 功能开关。
5. 真实设备试点还需要组织/司法辖区确认、正式告知/保留期限、有效证书/CA 托管、真实 Windows/Linux 测试机器、可撤销授权、安全/运维审核。没有这些条件不承诺上线日期。

## 工期：计划区间，不是承诺

以持续开发、规范已冻结、有授权测试环境和及时消除阻塞为前提，**v0.1 合成闭环可先以 4–8 周作为计划假设**；独立真实设备试点的准备可能需 2–4 个月；正式企业上线取决于试点、安全/隐私及运行恢复结果。每个里程碑应以验收证据评估排期，不能仅靠 UI 数量或 GitHub green checks 给出交付日。
