## Trust model and hard stop

- D-07 requires three independent DNS/SNI hosts: `console.lanveriq.internal`, `enroll.lanveriq.internal`, `agent.lanveriq.internal`. The Caddy **reference** deliberately returns 503 on console/enroll rather than deploying a login or pairing flow prematurely.
- Client-identity CA is separate from Caddy's internal **server** CA. The Agent TLS site requires a valid client certificate via `client_auth { mode require_and_verify; trust_pool file ... }`. Pilot explicitly supports **h1/h2 only**, enables `strict_sni_host on` and must not listen on UDP/443 or accept h3/QUIC. Do not change this to `request`, `require`, or `verify_if_given`.
- Before the Agent proxy sets `X-Lanveriq-Verified-Client-Fingerprint` from Caddy's certificate fingerprint placeholder, it strips the entire `X-Lanveriq-Verified-Client-*` family, `X-Forwarded-Client-Cert` and `SSL-Client-Cert`. The backend does **not** trust arbitrary `X-Forwarded-*` headers.
- `AgentIngressAssertionConfiguration` is now **fail-closed at bean startup** unless the opt-in backend connector explicitly has TLS enabled, `client-auth=need`, dedicated nonblank key/trust stores, `server.address=127.0.0.1`, `server.port=8443`, **only** `server.ssl.enabled-protocols=TLSv1.3` and `server.forward-headers-strategy=none`. Synthetic Java negative tests reject alternate/public addresses, ports, TLSv1.2/mixed protocols and forwarded-header modes. These settings are necessary, **not proof** of a real mTLS handshake or process isolation.
- `AgentIngressAssertionPolicy` is a **default-OFF internal component**. It checks canonical Agent Host, device route and POST, a single lowercase 64-char downstream Agent leaf fingerprint, no duplicated/aliased assertion headers, and loopback peer. **Crucially, it additionally requires `request.isSecure()`, the Servlet TLS peer certificate chain and constant-time comparison of the backend TLS client leaf's DER SHA-256 against an independently pinned Caddy proxy identity.** This check presupposes that Tomcat itself enforced TLS `client-auth=need` and a dedicated upstream-only trust store. The class is not an HTTP auth controller and does not validate real Agent credentials without subsequent PostgreSQL checks.
- **Upstream spoofing mitigation (unverified live):** the reference now uses `reverse_proxy https://127.0.0.1:8443` with `tls_client_auth` holding an independent Caddy-proxy certificate/key, `tls_trust_pool` verifying a separate Spring-backend server CA, and `tls_server_name spring-backend.lanveriq.internal`. Spring's **explicitly opted-in** profile demands `server.ssl.client-auth=need` (TLSv1.3), a backend server key store and a dedicated Caddy-client CA trust store. The assertion parser pins the expected Caddy TLS leaf digest. An arbitrary local process without that private key should fail the TLS handshake, regardless of forged HTTP headers. **This is only a design and unit-tested parser: no real handshake or network-boundary attack test has run.** Certificate/key ownership, file ACLs, key rotation, container namespaces and actual isolation need manual verification. If an unauthorized local user can read the proxy key or connect via a non-mTLS Tomcat listener, BLOCK deployment.
- The sample Caddyfile's Agent reverse proxy points to a still-denied Spring backend. It is documentation for the manual synthetic gate, **not a ready deployment configuration**.

**Caddy manual harness safety-hardening (2026-11-01, source only):** The synthetic [Caddy-only double-mTLS probe](../../deploy/caddy/tests/verify-reference.sh) now refuses occupied TCP 443/8443, creates a temporary loopback-bound Caddyfile without altering the reference, **verifies every adapted Caddy HTTP listener is exactly `127.0.0.1:443` before starting its host-network container**, and uses `docker run --rm`. The negative no-client-certificate/wrong-CA and direct-upstream probes must yield a **curl error with no HTTP response**; 403, 404, 502 and generic `not 200` are no longer accepted as proof of a TLS handshake rejection. The script verifies the valid independent upstream certificate succeeds before and after the negative cases and rechecks Agent→Caddy→synthetic-upstream success after rejected client certificates. A dead test server cannot satisfy the gate. This does **not** execute Caddy or change Spring/Agent operations. [The real manual workflow](../../.github/workflows/caddy-agent-mtls-synthetic.yml) must still be dispatched on the reviewed SHA and must pass its live Caddy 2.11.7 adaptation, mTLS and negative probes. The other [real Spring/Tomcat](../../.github/workflows/spring-upstream-mtls-synthetic.yml) and [combined bridge](../../.github/workflows/caddy-spring-postgres18-bridge.yml) manual workflows remain independent and unaccepted.

**Strict evidence scope:** This probe substitutes a deliberately tiny Python TLS server for Spring on port 8443.
