## Trust model and hard stop

- D-07 requires three independent DNS/SNI hosts: `console.lanveriq.internal`, `enroll.lanveriq.internal`, `agent.lanveriq.internal`. The Caddy **reference** deliberately returns 503 on console/enroll rather than deploying a login or pairing flow prematurely.
- Client-identity CA is separate from Caddy's internal **server** CA. The Agent TLS site requires a valid client certificate via `client_auth { mode require_and_verify; trust_pool file ... }`. Pilot explicitly supports **h1/h2 only**, enables `strict_sni_host on` and must not listen on UDP/443 or accept h3/QUIC. Do not change this to `request`, `require`, or `verify_if_given`.
- Before the Agent proxy sets `X-Lanveriq-Verified-Client-Fingerprint` from Caddy's certificate fingerprint placeholder, it strips the entire `X-Lanveriq-Verified-Client-*` family, `X-Forwarded-Client-Cert` and `SSL-Client-Cert`. The backend does **not** trust arbitrary `X-Forwarded-*` headers.
- `AgentIngressAssertionConfiguration` is now **fail-closed at bean startup** unless the opt-in backend connector explicitly has TLS enabled, `client-auth=need`, dedicated nonblank key/trust stores, `server.address=127.0.0.1`, `server.port=8443`, **only** `server.ssl.enabled-protocols=TLSv1.3` and `server.forward-headers-strategy=none`. Synthetic Java negative tests reject alternate/public addresses, ports, TLSv1.2/mixed protocols and forwarded-header modes. These settings are necessary, **not proof** of a real mTLS handshake or process isolation.
- `AgentIngressAssertionPolicy` is a **default-OFF internal component**. It checks canonical Agent Host, device route and POST, a single lowercase 64-char downstream Agent leaf fingerprint, no duplicated/aliased assertion headers, and loopback peer. **Crucially, it additionally requires `request.isSecure()`, the Servlet TLS peer certificate chain and constant-time comparison of the backend TLS client leaf's DER SHA-256 against an independently pinned Caddy proxy identity.** This check presupposes that Tomcat itself enforced TLS `client-auth=need` and a dedicated upstream-only trust store. The class is not an HTTP auth controller and does not validate real Agent credentials without subsequent PostgreSQL checks.
- **Upstream spoofing mitigation (unverified live):** the reference now uses `reverse_proxy https://127.0.0.1:8443` with `tls_client_auth` holding an independent Caddy-proxy certificate/key, `tls_trust_pool` verifying a separate Spring-backend server CA, and `tls_server_name spring-backend.lanveriq.internal`. Spring's **explicitly opted-in** profile demands `server.ssl.client-auth=need` (TLSv1.3), a backend server key store and a dedicated Caddy-client CA trust store. The assertion parser pins the expected Caddy TLS leaf digest. An arbitrary local process without that private key should fail the TLS handshake, regardless of forged HTTP headers. **This is only a design and unit-tested parser: no real handshake or network-boundary attack test has run.** Certificate/key ownership, file ACLs, key rotation, container namespaces and actual isolation need manual verification. If an unauthorized local user can read the proxy key or connect via a non-mTLS Tomcat listener, BLOCK deployment.
- The sample Caddyfile's Agent reverse proxy points to a still-denied Spring backend. It is documentation for the manual synthetic gate, **not a ready deployment configuration**.

## Opt-in executable synthetic Caddy acceptance (created, not run)

Run the **manually dispatched** [Caddy Agent double-mTLS probe](../../.github/workflows/caddy-agent-mtls-synthetic.yml) on `main`, or on an isolated Linux Docker host with `bash deploy/caddy/tests/verify-reference.sh`. It requires Docker, OpenSSL, Python 3, jq and an HTTP/2-capable curl. This intentionally does **not** run on push/PR and does not modify the Java unit-only CI policy.

The script uses pinned **Caddy 2.11.7** and creates disposable **P-256 synthetic** public/private certificates under a permission-restricted temporary directory. It uses separate Agent client, backend server, and Caddy-proxy client trust roots (plus a wrong-CA control); all materials are removed at exit. It adapts and validates the actual reference Caddyfile, checks adapted h1/h2 + strict SNI/Host and required client authentication, and starts Caddy in a disposable runner namespace. Its local Python HTTPS backend **requires** Caddy's separately trusted mTLS client certificate and inspects the forwarded synthetic Agent DER SHA-256 fingerprint.

Positive case: a legitimate synthetic Agent client certificate reaches the synthetic backend over Caddy→backend mTLS while attacker-supplied fingerprint and forwarded-certificate headers are stripped/overwritten. Negative cases: missing and wrong-CA Agent certificates, HTTP/2 cross-host Host/SNI mismatch (expect 421), and direct localhost backend probes without the Caddy upstream TLS client certificate or with a wrong-CA certificate. Server trust is verified with `--cacert`, **never `-k` / insecure skip-verify**. The workflow records the exact Git SHA, Docker image ID/digest and per-case PASS/FAIL. Logs must not include private keys, full certificates or real employee data.

**Strict evidence scope:** This probe substitutes a deliberately tiny Python TLS server for Spring on port 8443. Even a green manual Caddy run proves **Caddy + test TLS backend only**, not Spring Boot/Tomcat's `client-auth=need` connector, the servlet identity attribute, PostgreSQL revocation, Agent installation or organizational policy acceptance. These require an additional actual Spring runtime acceptance. A failed test must block enabling the Agent HTTP routes.

## Real Spring/Tomcat upstream TLS acceptance (NEW, MANUAL ONLY)

The separately dispatched [Spring Tomcat upstream-mTLS workflow](../../.github/workflows/spring-upstream-mtls-synthetic.yml) invokes `bash apps/server/scripts/verify-agent-upstream-tls.sh` on a dedicated GitHub-hosted Linux runner. It starts a **real Java 25 Spring Boot/Tomcat connector** with `agent-upstream-mtls-acceptance`, disposable PostgreSQL 18.6/Flyway V1–V8 and ephemeral P-256 server/proxy/wrong-CA leaves. All DB mappings stay loopback-only and the application binds only to loopback port 8443. No Caddy or actual Agent is started.

Cases require a valid CA- and DNS-verified TLSv1.3 client connection to `/actuator/health`, an actual TLS failure (no HTTP response) with no client certificate, wrong client CA or forged assertion header without a certificate, a **curl certificate-validation error** for the wrong backend DNS name, a default-403 business route even over authorized upstream mTLS, and absence of a plaintext listener on 8080 or plaintext success on 8443. The SHA-256 of the short-lived upstream client leaf is pinned to the opt-in internal policy bean; that bean does not expose a controller.

This isolated Spring test **does not prove** Caddy-to-real-Tomcat interoperation, the trust boundary across actual OS users/namespaces or proxy-key ACLs, per-request servlet-certificate extraction (the parser remains internal), PostgreSQL credential revocation at the HTTP edge, or deployed Agent behavior. An observed successful run must be recorded with exact SHA and image digest before closing only the specific **Tomcat upstream TLS** subgate. Failure blocks deployment and must not be bypassed by loosening client-auth, TLS verification or security routing.

## Caddy → real Spring/Tomcat → PostgreSQL 18.6 joint bridge (NEW; MANUAL ONLY)

To test the previously unobserved actual Caddy-to-Tomcat connection, manually dispatch [Caddy to real Spring Tomcat mTLS bridge](../../.github/workflows/caddy-spring-postgres18-bridge.yml) on `main`. The workflow sets `LANVERIQ_SYNTHETIC_CADDY_BRIDGE=1` and invokes the **same** `apps/server/scripts/verify-agent-upstream-tls.sh`; without that variable the standalone Spring probe stays unchanged. This is designed for a dedicated GitHub-hosted Linux runner, with Docker, Java 25, Gradle, OpenSSL, keytool, jq and HTTP/2-capable curl.

The extra mode takes the approved [Caddy reference](../../deploy/caddy/Caddyfile.reference) and makes a **temporary loopback-only copy** (127.0.0.1:443); it never alters the reference or listens on a LAN interface. It validates Caddy 2.11.7 adaptation for h1/h2, strict SNI/Host and `require_and_verify`, starts real Caddy in a disposable host-network container, Spring Boot/Tomcat TLSv1.3 on loopback 8443, and a loopback-published disposable PostgreSQL 18.6 container. Independent ephemeral P-256 trust chains cover Agent→Caddy, Caddy→Spring client identity, and the Spring server leaf. Test credentials, key stores and Docker containers are deleted on exit; the script prints image IDs/digests, not key material.

A legitimate synthetic Agent certificate **must reach the real Tomcat backend** but receive HTTP **403**, because Agent controllers remain disabled. An absent or wrong-CA Agent leaf must fail before HTTP; mismatched HTTP/2 SNI/Host must return **421**. Replacing Caddy's upstream client leaf with a wrong-CA leaf must produce **502**, as must making Caddy trust the wrong backend server CA. Restoring the legitimate trust chain must restore the backend **403**, not turn a denied endpoint into an allowed endpoint. The independent direct Tomcat test still checks no/plaintext/wrong upstream cert, server-hostname verification and no alternate 8080 listener. **All conditions fail closed; an HTTP 403 does not prove real Agent authorization.**

The joint probe **does not** test Spring's internal `AgentIngressAssertionPolicy.resolve` on an HTTP endpoint (no such route exists), strip/overwrite header contents (use the separate Python-backed probe), PostgreSQL-bound Agent credential revocation, actual two-network-namespace ACLs or operating-system key protection. An executed green run closes **only** the synthetic upstream transport/Tomcat/Flyway acceptance subgate, not a deployed Agent, full authorization or the whole D-07 gate. Keep all three workflows manual until the remaining gates and organizational authorization are accepted.

## Manual-only D-07 acceptance steps

Only on an **isolated synthetic test host**, after provisioning a public dedicated client CA certificate and separate server TLS trust roots:

1. Prepare **three independent trust domains** with synthetic test materials only: Agent→Caddy client-identity CA, Spring backend server-identity CA, and Caddy→Spring proxy client-identity CA; never reuse a private CA key or the Agent leaf. Start Spring only with the `agent-upstream-mtls-acceptance` profile and required `LANVERIQ_BACKEND_TLS_*` environment variables, pin the Caddy proxy **leaf DER SHA-256** via `LANVERIQ_CADDY_UPSTREAM_CLIENT_DER_SHA256`, and keep its private key out of the Spring process. Install a pinned Caddy build. Run `caddy adapt --config deploy/caddy/Caddyfile.reference --pretty`, inspect three SNI hosts, both TLS connections, `require_and_verify`, `strict_sni_host`, h1/h2 only, and header strip/overwrite. Run `caddy validate --config ...` with all actual synthetic test materials present.
2. Verify DNS, server certificate chains, HTTPS trust root, clock and SNI for each hostname; ensure console/enroll **never** accept the protected Agent identity assertion. Test a valid *synthetic* client P-256 leaf and require real TLS handshake success on agent only.
3. Test no certificate, wrong CA, expired/revoked leaf, wrong EKU, mismatched SNI/Host (including h2 connection coalescing), cross-host requests, h3/QUIC and UDP/443. All unauthorized paths must fail before access to any internal business operation. A TLS-trusted-but-DB-revoked credential must be rejected by PostgreSQL-bound service verification.
4. Attempt forged, repeated, upper/lower/underscore alias and malformed identity headers on all three hosts. Verify that Caddy strips client-supplied assertions and **overwrites** them only after actual mTLS proof; observe and compare a nonempty fingerprint with a DER SHA-256 digest of the synthetic leaf. Never log a real certificate or private key.
5. Try connecting **directly** to Spring on `127.0.0.1:8443` from an unprivileged local user and other namespaces with (a) plaintext HTTP, (b) ordinary HTTPS without proxy client certificate, (c) a self-signed/wrong-CA client certificate, (d) forged headers and (e) a stolen/revoked proxy test leaf. Every unauthorized attempt must fail TLS or be denied. Also test Caddy with a wrong backend server CA/SNI, verify its `tls_client_auth` private key is ACL-restricted, and prove **no alternate plaintext Tomcat connector** exists. Spring's `client-auth=need` and pinned proxy leaf are independent checks; loopback alone is insufficient. If any bypass succeeds, **BLOCK deployment**.
6. Run `cd apps/server && ./gradlew integrationTest` using actual disposable Testcontainers PostgreSQL 18.6 (or manually start the dedicated GitHub Action) to verify active/revoked/pending device binding. The normal unit CI does not execute Docker.
7. Maintain sanitized evidence: exact Git SHA, Caddy binary version and adapted config, trust-root identity, h1/h2 and connection-coalescing probes, accepted/denied request matrix, network isolation proof, database run link and image digest. Never upload real employee events or secrets.
