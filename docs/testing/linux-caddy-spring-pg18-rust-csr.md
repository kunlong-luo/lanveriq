# Linux Rust CSR → Caddy → Spring/Tomcat → PostgreSQL 18 synthetic L2 bridge

**Primary client OS: Pop!_OS 24.04/COSMIC.** This acceptance uses only an **isolated Ubuntu 24.04 GitHub-hosted runner**, not a real device, with temporary PKI and PostgreSQL 18.6. It does not install or start the production Agent, enable an enrollment/activation route, collect inventory, or authorize remote access.

## Exact acceptance boundary

The existing manual, synthetic-only `apps/server/scripts/verify-agent-upstream-tls.sh` harness previously demonstrated separately generated OpenSSL Agent certificates crossing Caddy and the real Java 25 Spring/Tomcat TLS hop. The existing **path-scoped combined workflow** `.github/workflows/linux-batch-a-caddy-pg18-acceptance.yml` now enables **both** `LANVERIQ_SYNTHETIC_CADDY_BRIDGE=1` and `LANVERIQ_SYNTHETIC_LINUX_CSR=1` on the disposable CI host.

The second flag is separately denied unless GitHub Actions and the synthetic Caddy mode are both present. It builds the **real Linux Rust `create_offline_p256_csr` helper** with the Agent's locked dependencies, calls it explicitly as the unprivileged CI user, verifies its signed PKCS#10 and private `0700` bundle / `0600` P-256 PEM, and uses only an ephemeral synthetic OpenSSL CA to issue a **one-day clientAuth-only** leaf with exact synthetic device `urn:uuid:00000000-0000-7000-8000-000000000001` SAN. The public key of the actual Rust CSR and the signed leaf must match byte-for-byte at normalized SPKI DER SHA-256. The private PEM is exported **only for this disposable test** to curl's temporary local `agent.key`, and the all-runner `TMP` tree, database and Caddy volumes are deleted by the existing cleanup trap.

The test then makes real TLS requests across:
`curl using Rust-generated client key/CA-signed leaf → Caddy 2.11.7 loopback TLS 1.3 mTLS → Caddy pinned upstream client cert → real Spring Boot/Tomcat TLS 1.3 client certificate verification → PostgreSQL 18.6`. Existing positive probes must return a **CA-verified 200/UP health** result. Protected Agent API must remain **403/default-OFF** even when both TLS peers are valid. The negative matrix must reject missing Agent certificate, wrong Agent issuer, incorrect hostname/SNI, untrusted upstream Caddy certificate, forged identity headers and plaintext backend exposure. All synthetic ports are loopback-only, with strict Caddy adapted listener checks.

The *separate* PG18 Testcontainers job proves transaction methods independently; it does **not** mean an actual TLS-authenticated request executed certificate registration → activation → heartbeat and exact ACK across the complete chain. The live application still starts with activation HTTP disabled. Certificate revocation and actual production Agent `reqwest` network transport remain separately gated. Never call this a real Pop!_OS acceptance or a production issuer/TPM/non-exportable key demonstration.

**Safety caveat:** Existing test Caddy mounts the ephemeral `TMP/pki` fixture directory read-only, and that tree includes test-only signing keys. This is limited to one disposable runner; production Caddy must never receive an Agent private key or an issuer private key. This test does not approve or model production key distribution.
