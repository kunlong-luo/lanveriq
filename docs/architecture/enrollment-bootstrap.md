# LAN bootstrap and device enrollment — v0.1 design

**Status:** D0-approved V0.1 technical design; no runnable installer, provisioned CA or tested certificate lifecycle. Device enrollment occurs only on managed, notified organization equipment. For operational simplicity, use a verified set of purpose-separated LAN hostnames in the D-07 selected technical design below; never infer trust merely from a local IP address.

## Server TLS design (D0 baseline, not yet configured)
- One Caddy service with purpose-separated HTTPS hosts (D0-selected pilot names: console/enroll/agent.lanveriq.internal; provisioning DNS, actual TLS policy and Caddy validation remain required implementation work).
- **Selected pilot server trust approach:** Caddy `tls internal` as a private server CA (independent of the dedicated offline client-identity CA). Install the CA root into the operating-system trust store on each managed endpoint/admin workstation **through a verified, authorized channel** and verify its fingerprint out-of-band.
- Caddy in Docker may not install its root into the **host/endpoint** trust stores automatically. Treat that as a provisioning task, **never bypass verification** with insecure TLS flags.
- Protect and back up CA private keys securely; establish rotation and disaster-recovery procedure. Production may replace Caddy internal CA with an organization-managed PKI.
- Public network ports: HTTPS only for authorized LAN/VPN segments. Never expose PostgreSQL or internal management endpoints.

See [Caddy internal TLS documentation](https://caddyserver.com/docs/caddyfile/directives/tls) for limits of automatic trust installation.

## D-07 selected pilot technical architecture (NO LIVE PKI TESTED)

**SRV-02 implementation progress (2026-10-30):** Internal `PendingEnrollmentService` now validates canonical one-use token, checks PKCS#10 signature and P-256 public key through maintained Bouncy Castle 1.86, and calls a Spring/JPA transaction to conditionally consume that token and create a PostgreSQL UUIDv7 device plus pending public CSR. Flyway V3 adds unique CSR SPKI and digest/size constraints. This is **unit-tested only** ([CI](https://github.com/kunlong-luo/lanveriq/actions/runs/41065309965)); PostgreSQL V1–V3 migration, locking/rollback, DNS/Caddy host isolation, notices, abuse controls, offline CA signing, certificate registration and mTLS activation are **NOT TESTED OR NOT IMPLEMENTED**. No public device pairing endpoint is exposed. **2026-10-31 implementation addendum:** the internal `DeviceActivationService` now stages the reviewed-pending-credential → active JPA transaction and same-certificate idempotent retries, with synthetic JUnit and opt-in PostgreSQL checks. A default-OFF internal PKIX validation and scoped review/registration transaction is now staged (using only an independently pinned public client CA and synthetic tests), but no real offline CA/leaf workflow, trusted mTLS identity bridge, HTTP activation or PostgreSQL execution has been verified. See [SRV-02 registration test plan](../testing/server-cert-registration-manual.md). See [SRV-02 activation test plan](../testing/server-cert-activation-manual.md).

**D0 pilot ingress naming baseline (approved default names, DNS not yet provisioned):** The deployment uses `console.lanveriq.internal`, `enroll.lanveriq.internal` and `agent.lanveriq.internal`. These three DNS records and the matching server-TLS certificates must actually resolve/validate on the managed LAN before a device is enrolled. A different organizational domain may be configured **only if all three separation, certificate and Origin rules remain intact**; never silently combine site boundaries.
- `console.lanveriq.internal:443` serves the same-origin browser SPA, session-authenticated REST and `/ws` WSS. No client certificate requirement; strict Origin, session, CSRF and role/group checks.
- `enroll.lanveriq.internal:443` serves **only** bounded initial enrollment/certificate-pickup operations. TLS server identity is mandatory, but a not-yet-enrolled device cannot be required to supply a client certificate. One-use token, CSR proof-of-possession, authorization/notice binding, throttling and short expiry apply.
- `agent.lanveriq.internal:443` serves **only** enrolled Agent heartbeat, event batches, inventory and approved agent endpoints. Its TLS listener/site requires `client_auth { mode require_and_verify ... }` against a **dedicated client-identity CA**. Other site hosts/paths must not proxy the protected Agent handlers. Separate site names do not by themselves prove correct SNI/TLS policy isolation; validate Caddy's adapted configuration, actual browser/Agent TLS handshakes and connection reuse.

**Selected pilot certificate issuance (low-volume, human-operated; no bespoke CA service):**
1. An authorized operator provisions the **server-trust root** out-of-band with the real hostnames/fingerprint; Caddy internal PKI may be used for *server* TLS only. Keep a separate **client-identity signing CA**, with encrypted/offline signing key and a backed-up recovery procedure.
2. Agent locally generates a per-device private key and CSR. The first-time installer submits the CSR with the short-lived one-use enrollment token and acknowledged notice to the **enrollment** host. PostgreSQL atomically consumes the token, assigns canonical UUIDv7 `device_id` and records **pending_certificate**, not `active`. Validate CSR signature, key algorithm, length, size and rate limits.
3. A scoped security admin reviews the pending device/group and retrieves its persisted CSR via **console-only `GET /api/v1/devices/{id}/enrollment-csr`**. The operator independently verifies its digest and **manually signs the CSR** using maintained `step certificate sign --template ...` with an issuer-owned **clientAuth-only** leaf template (CA=false, digitalSignature, bounded lifetime and authoritative device-ID subject/SAN; no CSR-requested identity copied blindly). The default `step` TLS leaf template is **not** safe to adopt unchanged for client-only certificates because it may permit serverAuth too. The admin then registers the signed public leaf/chain via **console-only `POST /api/v1/devices/{id}/client-certificates`**: Spring verifies approved issuer, SPKI match with stored CSR, authorized device identity, validity, fingerprint uniqueness and pending status without ever possessing the CA signing key. Only the public leaf/chain is delivered to the installer through a verified provisioning channel. The private key never leaves the Agent and the CA signing key never moves to the public web service.
4. Agent calls **`POST /api/v1/devices/{id}/activate`** over **mTLS** on the Agent host (the **only** request allowed for its registered `pending_certificate` credential). Caddy validates the leaf chain, while Spring checks verified proxy fingerprint, exact pending `device_id`, unexpired status, credential binding and allowed activation route, then atomically marks it `active`. Subsequent heartbeat/event/inventory routes **require active state** and re-check the binding on every request. A lost enrollment response/token requires a new admin-approved attempt; do not silently reuse consumed tokens.
5. For 1–10 endpoints, operator-mediated certificate installation is an explicit UX/operational cost. An automatic online CA (e.g. reviewed step-ca) is **not part of the approved V0.1 baseline** and requires a separate reviewed design change. No hand-rolled X.509 issuer.

**Pilot transport policy:** configure Caddy's HTTPS server listener explicitly with `protocols h1 h2` and `strict_sni_host on`; do not enable HTTP/3/QUIC for the initial Agent mTLS pilot, and block UDP/443 on the LAN gateway. All three hosts use TCP/443 with distinct TLS client-auth policies; `agent` must use `client_auth { mode require_and_verify; trust_pool file <dedicated-client-ca> }` (configuration *illustration*, not a runnable Caddyfile). Caddy 2's `strict_sni_host` verifies that the HTTP Host matches TLS ClientHello SNI and is automatically enabled when client auth is configured, but we deliberately require it explicitly. Reject SNI/Host mismatch, protocol confusion and direct Spring port access. Do not assume a closed upstream or documentation proves the policy: run `caddy adapt`, `caddy validate`, protocol-negative probes and cross-host HTTP/2 tests after implementation. HTTP/3 may only be enabled later after separate mTLS/route isolation review and testing.

**D0 client-certificate profile:** approved pilot CSR key algorithm is **ECDSA P-256**, signed by the dedicated client CA through an issuer-owned clientAuth-only template (no serverAuth; `CA=false`, digitalSignature). The only authoritative URI SAN is `urn:uuid:<server-assigned-device_id>`; it is inserted from the **server's pending enrollment record**, never copied from the CSR. Pilot leaf lifetime **90 days**, renewal request/review at least **30 days before expiry**; old and replacement fingerprints may coexist only during documented, time-limited rotation, and revocation always overrides chain validity. The database stores the SHA-256 digest of the DER-encoded leaf certificate as **64 lowercase hexadecimal characters**; Caddy's `{http.request.tls.client.fingerprint}` must be verified to emit exactly this format on an actual validated mTLS request. Any supplied but untrusted CSR SAN/CN value is ignored for identity. These are approved **design choices**, not operating PKI evidence.

**Caddy → Spring assertion boundary:** strip **every** client-supplied `X-Lanveriq-Verified-Client-*` identity header on all three ingress hosts. Only after successful **mTLS on the Agent TLS connection** may that ingress **overwrite** (never append or forward an untrusted duplicate) the exact server-owned `X-Lanveriq-Verified-Client-Fingerprint` header with the documented Caddy `{tls_client_fingerprint}` / `{http.request.tls.client.fingerprint}` value. Agree on its byte format and fingerprint algorithm with the database record; reject empty, malformed or multiple headers. **Do not forward a client-controlled fingerprint into the protected service from console/enroll.** Spring listens only on an isolated non-public upstream, checks the trusted request's ingress class, allowed route and fingerprint against active/pending DB state on **each** request, and rejects all LAN/direct-backend access. Enforce Host/SNI ingress boundaries and test HTTP/2 connection coalescing/host-header mismatch; distinct hostnames alone are **not** authorization. Use Caddy's supported `header_up` overwrite with its verified TLS placeholder, then inspect the adapted config and run negative TLS/Host-header tests. Chain validation alone is **not** device revocation: Spring DB checks must deny revoked credentials immediately, even on reused connections.

**Key custody and rotation baseline (verify on target OS after D0):** Windows: service-identity-restricted key material protected by OS ACL and, where compatible with reqwest/rustls, DPAPI encryption at rest; Linux: service-account-only mode 0600/0700 local storage with host disk encryption where available. Do **not** promise non-exportable Windows CNG keys work with rustls until explicitly demonstrated. No private keys in SQLite, logs, repo, browser storage or CLI arguments. Pilot leaf lifetime is 90 days with operator-led renewal initiated at least 30 days before expiry; overlap old/new credentials only during a bounded audited transition, and a revoked old credential must fail immediately. Record recovery from compromised issuer/key, damaged Agent database, expiration and isolated CA backup restoration. Final validity/key-storage choices remain subject to D-07 sign-off.

**Required negative evidence after implementation:** browser/pre-enrollment unaffected by Agent mTLS; unauthenticated, wrong-CA, forged or repeated forwarded headers, mismatched SNI/HTTP Host and cross-host HTTP/2 requests, wrong device ID, expired, rotated/revoked and cross-group credentials rejected; signed leaf with wrong EKU, subject/device ID, issuer, validity or CSR public key rejected during registration; direct Spring route bypass impossible; stolen/reused enrollment token rejected; a pending certificate cannot heartbeat before mTLS activation; revoked active connections cannot continue uploading; trust-root mismatch fails closed. Document dates, Caddy version, OS/crypto backend and observed results.

Official reference: [Caddy TLS client authentication](https://caddyserver.com/docs/caddyfile/directives/tls), [Caddy reverse-proxy header controls](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy), [Smallstep CSR signing](https://smallstep.com/docs/step-cli/reference/certificate/sign/). This is an **architecture proposal**, not a tested Caddyfile or approved PKI operation.

## Bootstrap and credentials
1. Start server with a **single-use admin setup secret generated locally**, constrained to a private host console or similarly controlled setup. No shipped universal password.
2. Administrator enrolls with protected credentials; other accounts created only through authenticated role-managed flows. Configure password storage, sessions and lockout/rate limiting.
3. Admin creates a short-lived, one-use enrollment token associated with a device group and immutable disclosed policy version. PostgreSQL stores only a verifier/hash.
4. On the endpoint, the trusted admin installer checks server hostname and certificate chain, displays the organization notice and obtains pairing approval.
5. Agent generates a unique asymmetric key and valid CSR; the server **atomically consumes the token and allocates `device_id` in `pending_certificate` state**. There is no client certificate or active credential thumbprint yet.
6. An authorized operator reviews and signs the CSR using a reviewed client-CA workflow, registers the resulting certificate fingerprint against that device ID, and delivers only the signed certificate/chain to the approved installer. Keep a **bounded expiry and administrator cleanup** for abandoned `pending_certificate` enrollments. This human step is an explicit proposed V0.1 pilot workflow, not an implemented certificate-issuance service.
7. Agent proves possession using the dedicated **mTLS activation endpoint** on the separate Agent ingress. Spring checks the Caddy-verified certificate fingerprint, exact pending credential and device ID before committing the transition to `active`; only then accept heartbeats. Revocation, key rotation, expired certificates and lost key/DB require audited repair; no fallback long-lived shared API password.

## Identity lifecycle
New install -> token-validated `pending_certificate` -> signed credential registered -> first verified mTLS proof -> `active` -> revoked/retired. Incomplete/expired pending requests remain unable to upload. If local identity and SQLite are lost, a new enrollment creates a **new device_id**. Administrators may record an explicit replacement link to the old record; never stitch together two event sequence histories.

## Failure behavior
Invalid/missing trust root: refuse connection. Used/expired token: refuse pairing. Duplicated device public key, duplicate CSR/credential binding, abandoned pending enrollment or enrollment conflict: require explicit administrator action. Server unreachable: keep previously enrolled and buffered events in bounded SQLite, without collecting newly unauthorized data.

## D0 baseline decision versus deployment proof
The D0 technical selection is specified above: three role-separated hostnames, h1/h2-only, strict SNI/Host, dedicated offline client CA, operator-approved CSR issuance, ECDSA P-256/90-day clientAuth-only leaves with `urn:uuid:<device_id>` SAN, verified SHA-256 DER fingerprint and DB revocation. D0 approval does **not** show that DNS, a signing CA, Caddy configuration, a protected OS key store or any live deployment already exists. These are **mandatory post-D0 engineering acceptance conditions** under [D-07](../governance/open-decisions.md) and the [D0 gate](../governance/documentation-gate.md).
