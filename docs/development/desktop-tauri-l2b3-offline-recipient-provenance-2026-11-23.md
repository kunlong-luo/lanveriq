## Architecture and evidence hierarchy

The preceding GUI-only native Debian candidate, source-only SPDX receipt and ephemeral laboratory Ed25519 detached-receipt signature were actually verified at function SHA ce1a9c26, [native run #45161801144 SUCCESS](https://github.com/kunlong-luo/lanveriq/actions/runs/45161801144). They do **not** establish an independent release signer or an attestation chain.

For the future real release, **reuse GitHub CLI** (the maintained Sigstore-aware verifier) for cryptographic provenance, rather than custom Ed25519/DSSE implementations. GitHub documents [offline bundle and root handling](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline) and [gh attestation verify constraints](https://cli.github.com/manual/gh_attestation_verify). The GitHub docs explicitly caution that repository name alone can be reused after a rename; offline verification needs the certificate's **numeric repository ID** as well. The repository ID currently returned from GitHub API for kunlong-luo/lanveriq is **1439447217**; pinning this in source is a preliminary consistency check, **not** an independently approved trust anchor.

[Recipient-side verifier](../../apps/desktop/tools/verify_desktop_offline_provenance.py) requires a regular, audited lanveriq-desktop_0.1.0_amd64.deb, an offline attestation bundle, an independently delivered Sigstore trusted-root file and explicit out-of-band SHA-256 pin of that trusted root, plus an expected immutable source commit. It performs strict GUI-only Debian archive checks, then calls *gh attestation verify* using --repo kunlong-luo/lanveriq, --bundle, --custom-trusted-root, --source-ref refs/heads/main, --source-digest, --signer-workflow, --predicate-type SLSA provenance v1, --deny-self-hosted-runners and --format json. After gh cryptographic success it requires exactly one verified statement, matching certificate sourceRepositoryIdentifier and sourceRepository, a verified timestamp, exact one named subject and exact package SHA-256. GH OIDC issuer is pinned to token.actions.githubusercontent.com. Refuse absent/malformed/root-mismatched inputs and CLI failure.

**The fixed proposed signer** is kunlong-luo/lanveriq/.github/workflows/desktop-release.yml. This dedicated release signer workflow **does not yet exist and is NOT approved**. Existing desktop-deb-candidate.yml must not produce official attestations. An actual trusted root is **not** present in the repository; no live attestation is published or downloaded. The verifier cannot legitimately accept any currently produced GUI package as a signed release. Tool input from the future is not authorization to install, enable, distribute or mark release ready.

## Test design and what is NOT proved

The [receiver tests](../../apps/desktop/tools/test_verify_desktop_offline_provenance.py) use synthetic Debian archives and mocked GH success JSON to check strict argument construction, expected workflow/ref/commit, numerical repository ID and certificate name, timestamp, SLSA predicate, subject name and digest, missing/symlinked files, root pin mismatch and other refusals. **A mocked successful GH response proves only wrapper control flow, not signature validity**; CI explicitly labels it as such. The workflow also calls **real gh CLI** on an intentionally fake bundle/trust root to require rejection. No test injects a fake Sigstore trusted root as an approved publisher or claims it is real evidence.

Passing this preflight is **L1 offline intake and negative contract readiness only**, not L2 actual independently verified trusted provenance. Before a trusted release can exist, an independent security/release authority must approve immutable signer workflow and workflow protections, actual Sigstore trusted root acquisition plus external pin/rotation/revocation and trusted time policy, a complete delivered-artifact/runtime SBOM, independently sourced repository ID and high-water downgrade policy, release publication/attestation privacy, reviewer dual control, and recipient-side tests using a real approved offline bundle. Organization must separately approve installation helper/polkit and real Pop!_OS 24.04 hardware.

No production signing keys, GitHub OIDC identity/write permission, release publish, install, service enable, Agent collection/network or remote control have been enabled. G-02/G-05/G-07/G-08/G-09 remain OPEN; **v0.1 NOT RELEASE READY**.
